# 第三方平台一次性接入 go-ah 统一认证

依赖skill: sql-harness
> 用于核对认证中心侧的 `o_auth_clients` 注册行，以及在接入方数据库上执行/校验身份映射建表。
> **若 sql-harness 无法加载，立即终止本 skill 并提示用户先安装或修复该依赖**，不要用裸 psql 或临时脚本绕过。

## 这套流程解决什么

接入本身不难，难在**接完之后能不能拿到原有用户的数据**，以及**上线后才发现登录 404**。
本 skill 的每条硬判据都对应本次真实踩过的一次返工。

四条不可妥协的设计决策（改之前先读 [[A03-账号映射与数据库陷阱]]）：

1. **身份主键是邮箱，不是 `sub`。** 顺序反了，"先用邮箱密码注册、之后才在认证中心建号"的人
   首登会被自动建出一个空账号并被 `sub` 永久绑住，老数据再也回不来。
2. **归属变化绝不静默。** 邮箱与既有 `sub` 绑定分叉时按邮箱改绑，但必须落 `warning` 日志 +
   响应回带 `rebound=true`；被放弃的账号一行数据都不删。
3. **refresh_token 一律不落地，会话过期就重新走授权。** 认证中心的 `access_token` /
   `refresh_token` 是不透明串、只有 `id_token` 是 RS256 JWT。本平台之所以能定这条硬约束，是
   两个平台事实叠加：① 5 个注册客户端全是 public 且无 secret，发现文档也无 DPoP / mTLS，
   所以这串凭据**谁拿到谁可用 7 天**，服务端加密存也只是看起来不可读；② 静默续期 + 滑动会话
   会让用户**永远不再回到认证中心**——统一登出、周期性重新确认身份、策略变更生效全都形同虚设。
   注意这**不是协议立场**：RFC 9700 禁的是把 refresh token 暴露给浏览器/设备端，机密客户端在
   服务端持久化是通行做法。分层判据与失效条件见 [[A02-业务侧代码骨架]] 的"会话与续期"，
   那里同时标注了本仓库自带模板与这条规范冲突之处。

   **移动端的具体形态不是"存一个短 token"，而是持登录态。** App 需要能批准扫码、
   又需要能静默换业务 token —— 这两件事回答的是同一个问题（这台设备是否已登录），
   所以用 `idp_session` 而不是 access_token：它在服务端是 `user_sessions` 一行，
   **可被立刻吊销**，而 App 不是任何人的依赖方，为它维持一条 token 生命周期毫无必要。

4. **一个凭据只服务一个用途。** 这是本轮付出最大的一次返工：把"业务会话"和
   "一次性动作身份"压在同一枚 10 分钟 access_token 上，它同时满足不了两边，
   于是衍生出「要不要存 refresh_token」「失效太快要不要调平台级 TTL」两层伪问题 ——
   **那都不是需求，是第一个错误的派生物。** 摆正分工（登录态 / 业务 JWT 各一）之后，
   那两个问题不是被解决了，是不存在了。
   配套纪律：凭据类型不要退化成裸 `String` 形参在多层间传递 ——
   把凭据从函数签名里拿掉、由实现自己从注入的存储取，传错就会编译失败。
   详见 [[A05-扫码登录与移动端批准]]。

## 前置确认（缺一项就不要开工）

| 项 | 为什么必须问 | 别猜 |
| --- | --- | --- |
| 接入方是什么形态：纯 JSON API / 有前端 / CLI | 决定"谁发起跳转、谁存 PKCE verifier"，方案完全不同 | 默认假设"有前端"会做出无法验证的实现 |
| 认证中心对外 issuer 地址与端口 | issuer 必须与 `IDP_ISSUER` 逐字一致，且是**浏览器可达**地址 | 后端端口 18080 能返回发现文档，但浏览器跳过去是 404 |
| 身份主键策略 | 邮箱优先 or sub 优先，二者不可兼得，且事后改会有数据归属迁移 | 见决策 1 |

| 目标库是不是生产 | 决定测试与验证能不能真跑（本次是线上库 + 只回滚不删除） | 在线上库跑带 DELETE 的旧测试会删真实账号 |

## 五阶段流程

每阶段做完立刻核"硬判据"，不通过就停下修，**不要往下走**——第 4 阶段的失败往往源自第 1 阶段的地址错。

### 阶段 1 · 认证中心注册 client

在 `auth_hub.o_auth_clients` 建一个**公共客户端**：`is_public=true`、`pkce_required=true`、
**没有 `client_secret`**。`redirect_uris` 是空格分隔存储、API 层收数组，匹配是**精确到路径**的，
只有 `127.0.0.1` / `localhost` 允许端口通配。

**硬判据**：拿 `/oauth2/auth` 探测——登记的地址返回 302，随便编一个外部地址返回
`400 redirect_uri 未在客户端注册白名单内`。这一条**不需要管理端凭据**，是证明注册生效的最强证据。

### 阶段 2 · 业务侧配置

配置块 + 环境变量覆盖（`<PREFIX>_OIDC_ISSUER` / `_CLIENT_ID` / `_REDIRECT_URI` / `_ENABLED`）。
**凭据和地址不要写进进 git 的配置文件**，容器一律用 env 注入。开关关闭时接口必须短路、
完全不碰网络。

**硬判据**：`GET <业务>/…/oidc/config` 返回 `idpAvailable=true` 且 `authorizationEndpoint`
来自发现文档（不是自己拼的），说明服务端到服务端可达认证中心已成立。

### 阶段 3 · 本地实现登录

分包：协议层（换 token + 验签，只用 `coreos/go-oidc` 不自解 JWT）与身份落地层
（映射 / 认领 / 建号 / 签发本系统凭据）分开。身份落地必须整段包在事务里，唯一索引兜并发。
签发出的凭据要和原密码登录**同构**，这样下游鉴权链路一行都不用改。

**硬判据**：`SQLH=1` 那组用例全绿，且其中至少包含"接管既有账号能读到自己的数据"和
"二次登录不重复建号"两条——这两条覆盖 90% 的接入事故。

### 阶段 4 · 一次性验收

一趟真实链路：认证中心登录 → authorize → consent 拿 code → 业务侧 callback → 带返回的
凭据调受保护接口。外加两条安全断言：**同一 code 重放必须被拒**、**换错 verifier 必须被拒**
（后者顺带证明你的 PKCE 实现与认证中心互操作正确）。

**硬判据**：[[A04-一次性验证与排错]] 的 10 项断言全通过。

### 阶段 5 · 上线

部署前先确认三件事：`redirect_uris` 与实际对外地址一致；镜像内的配置真的带上了新键
（有的部署会挂宿主机旧配置，那样加了也不生效）；迁移已在目标库执行过。

**硬判据**：部署后再跑一遍阶段 2 与阶段 4 的判据（地址换成线上），本地通过不等于线上通过。

## 错误案例（本次真实付出过代价的）

| 错误操作 | 实际后果 | 正确做法 |
| --- | --- | --- |
| 身份判定按 `(issuer,sub)` 优先 | 老用户被绑到新建空账号，原有数据再也拿不到（等于白接入） | 邮箱命中优先，`sub` 绑定只作辅助；用回归用例钉死 |
| 昵称"每次登录无条件跟随认证中心" | 线上真实账号昵称被覆盖，且此后该字段再也改不动 | 仅当本地为空时补齐，认证中心当前值只进快照列 |
| issuer 填成后端端口（如 18080） | 发现文档能拉到，浏览器跳转却 404，登录永远起不来 | issuer 用 nginx 对外地址；以 `idpAvailable` + 302 探测双验 |
| http 明文环境下直接写 `crypto.subtle.digest` | 非 secure context 下 `crypto.subtle` 是 undefined，页面静默失败 | 自带 SHA-256，并用 Node 对拍 + 从素数根独立推导魔数表校验 |
| 空邮箱写入 `users.email=''` | 撞 `WHERE email IS NOT NULL` 部分唯一索引，第二个无邮箱用户建不出来 | 空值一律写 NULL |
| 自动建号只插一行 users | 新账号没有默认工作空间，KV/文件等按组归属的功能全部不可用 | 复刻完整注册流程（工作空间 + 邀请码 + 回填默认组） |
| 相信"迁移里写了 REFERENCES 就等于有外键" | 线上 `user_groups` 一个外键都没有，35 个孤儿组；新账号还会回收旧 id | 用 `pg_constraint` 实测；序列 `setval` 到 `max(id)` |
| 在线上库跑带 `DELETE` 清理的旧集成测试 | 删掉带邮箱的真实账号 | 改用"必定回滚的外层事务 + 独立连接复查零残留" |
| 本地落后远端却想 force push | 抹掉别人的提交 | 先 `git fetch` 看 ahead/behind，rebase 后核对 diff 是纯增量 |
| 客户端持久化 `refresh_token` 并做静默续期 | 配合滑动会话，用户永远不会再回到认证中心：统一登出、周期性重新确认身份、认证策略变更全部失效；一份 7 天有效、且不绑 secret 的凭据长期躺在存储里，泄露面被拉到最大 | 不存 refresh_token；会话过期就重新 302 授权（IdP 全局会话 30 天内是无感跳转，活跃用户由看门狗自动续期） |
| 把"本仓库模板里加密存了 refresh_token"当成推荐做法照抄 | 模板那套在有 secret 或 DPoP 的平台上是可辩护的，但本平台两条都不提供，照搬过来等于把"谁拿到谁可用 7 天"的凭据长期入库 | 见 A02"会话与续期"的分层判据：加密只改变可读性、不改变凭据本身无绑定这个事实；本平台一律不存 |
| Windows 下 curl 内联中文请求体 | 远端存进去是替换符 U+FFFD | 用 UTF-8 文件 + `--data-binary @file` |
| 一枚 access_token 同时当"业务会话"和"扫码身份"用 | 10 分钟有效期两头都不够，接着就要么存 refresh_token、要么调平台级 TTL —— 全是派生问题 | 先摆正凭据分工再动手；用调安全参数修客户端体验是反向操作 |
| 手机侧端点保留 `String accessToken` 形参、只改语义去收登录态 | 调用方继续传业务 token 仍通过类型检查（都是 String），要等运行时 401 才发现 | 把凭据从签名里拿掉，端点自己从注入存储取 —— 编译器比约定可靠 |
| 给"设备画像为空"写测试时只测响应解析（喂理想 payload） | `preview()` 少写 `/preview` 后缀打到 PC 侧轮询端点，200 且 `code=0`、只是没有 `pc` 字段，功能整体静默不可用而测试全绿 | 用 MockClient 钉住实际请求 path，逐端断言 |
| 把 `expires_in` 和 `status` 一起遮蔽（"无凭据者什么都不给看"） | 前端倒计时塌成"0s 后失效"；不报错不拒绝，只是把用户挡在门外，最难归因 | 遮蔽只针对"进展到哪一步"；剩余寿命不是秘密，建票时已公开 |
| 新加的安全断言直接宣称"已验证" | 其中一条在依赖服务不可达时是跳过，那次「All tests passed」什么都没验证 | 安全断言一律做负向对照：拆掉被守卫的实现 → 必须变红 → 恢复 → 复验 |
| `go build 2>&1 \| head -20 && echo OK` | 管道吞退出码，构建失败也报 OK；本轮两次被误导 | 判成功用不带管道的 `&&`；格式化用 `gofmt -l` 无输出复验 |
| 改共享类（`TokenStorage`/`TokenManager`）的类名与构造签名 | 打断了三处与本次无关的调用点 | 让新设计适配既有接口，而不是反过来；改共享签名前先 grep 全部使用方 |

## 成功标准检查清单

- [ ] 客户端是 public + PKCE required，且**没有** `client_secret`；token 端点也没在校验 secret
- [ ] `redirect_uris` 精确到路径，且覆盖线上地址与本地 loopback 通配两类
- [ ] 业务侧配置里的 issuer 与认证中心 `IDP_ISSUER` 逐字一致，是浏览器可达地址
- [ ] 身份主键是邮箱；接管既有账号时不改 `users.email`、不覆盖非空 `users.nickname`、不清 `password`
- [ ] 改绑有 `warning` 日志且响应回带 `rebound`；被放弃账号不删任何数据
- [ ] 自动建号复刻了完整注册流程（默认工作空间 + 邀请码）
- [ ] 签发的凭据与原密码登录同构（下游鉴权零改动）
- [ ] 协议层不自己解 JWT；验签交给 SDK
- [ ] **客户端与会话存储里都没有 `refresh_token`**：不落浏览器存储、不落客户端本地文件/键
      盘、后端会话表也不存；没有"后台静默续期 + 会话滑动延长"这套机制
- [ ] 会话过期路径已实测：业务会话过期后重新 302 授权能无感拿回登录态（不要求重输密码）
- [ ] 验收覆盖了：接管、二次登录不重复建号、code 重放被拒、verifier 不匹配被拒
- [ ] 在线下/线上库上跑的测试不落任何数据、不做 DELETE，并有独立复查
- [ ] 凭据只走环境变量注入，明文凭据没有新增进 git
- [ ] 部署后重新跑过一遍验收（本地通过 ≠ 线上通过）
- [ ] 每份凭据只有一个用途，且没有以裸 `String` 形参在层间传递（传错应编译失败）
- [ ] 新增的每条安全断言都做过负向对照（拆掉防线能变红）
- [ ] 端点测试钉的是实际请求 path，不只是响应解析
- [ ] 依赖外部服务的测试，其"跳过"与"通过"在汇报里区分清楚
- [ ] 修改过共享类型的签名前，已 grep 全部使用方并确认未打断无关代码

| 错误操作 | 实际后果 | 正确做法 |
|---------|---------|---------|
