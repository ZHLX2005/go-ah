# B01 · 完整统一登录接入链路

> 把 mn-rt + fr + go-ah 三件套的"用户在哪一步做了什么、服务去哪一跳拿了什么"摊开来看。每个节点给 file:line 锚点，验证时顺着读代码就能复现完整链路。

## 加载时机

- 排查一次登录涉及的链路时（"为什么我点了登录没反应 / 为什么 401 / 为什么 state 不匹配"），先按本 ref 定位代码再翻 A04 的故障对照表
- 给新接入方讲解生态全景时（比 A02 的"业务侧代码骨架"更高一层的鸟瞰图）
- 评估改造影响面（动其中一段要影响哪些仓库的哪几行）

## 一条核心原则

**任何人都只在协议层做 PKCE 校验，谁也不持久化 refresh_token**——CLI 换 token 用完即弃；fr 根本不接触 IdP token；mn-rt 服务端拿 access_token 验完身份就丢；refresh_token 即便被 IdP 颁出来也在协议层不进入任何应用态。这条原则把整条链路串起来，每个跳都遵守。

## 链路图

下表的 `→` 表示"客户端调用 / 跳"，箭头方向是请求方向。**第 N 步同列的文件就是这一步的代码所在地**。

要点：

- **CLI 一人不碰 IdP 账户**：拿到的 access_token 只用一次（验身份→签设备令牌→丢），refresh_token 当场不存（拿不到、也不存）
- **loopback 回调地址不是"传用户信息"，是"送一次性授权码"**：userinfo 拿到 sub 是第 ⑫ 跳服务器自己问 IdP，CLI 说的不算
- **sessionKey 11 不动 13 动**：服务端在 ⑫ 那把由属主拿，⑬ 持久化到本地；⑮ 注册 ack 再下发同一把（`sessionKey` 字段），用户感觉不到 PKCE 与 PKCE 之后还有什么别的"配对 key"

要点：

- **App 根本不接触 IdP token**：mintCodeForClient 只产 code；拿 token 那步是 mn-rt 服务器去问 IdP；App 收到的是 mn-rt 自己签的用户令牌
- **consent 自动同意**：同一管理域内部第一方客户端，App 跳过"看到授权页"，这是 RFC 9700 标准允许的第一方豁免（详 B02）
- **userToken 不绑设备**（cid = ""）：手机换号重装、登出再登另一台都不需要重新铸码；但凭据与账号强绑定，凭据丢了需要重新授权
