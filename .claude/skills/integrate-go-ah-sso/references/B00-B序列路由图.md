# B00 · B 序列路由图

> B 序列把"统一登录"这个主题从**接入者侧**（A 序列：注册 / 写代码 / 落库 / 验收 / 扫码）切换到**架构关系视角**（链路全景 / 自提供 IdP / 客户端模型 / refresh_token 归属）。
> 同一个 skill、两种切法，互相不重叠而是互补。

## 为什么需要 B 序列

A 序列回答的是**"我作为新接入方，怎么把对接走完"**：

| A | 视角 | 提问 |
|---|---|---|
| A01 | 认证中心侧 | 我要在认证中心注册一个 client，该填哪些字段、不能踩哪些坑 |
| A02 | 业务侧 | 我要在自己的服务里写代码，落库该用哪个 schema |
| A03 | 账号映射 | 用户在我这里没账号时，该怎么从 sub/email 决定归属 |
| A04 | 验收 | 怎么证明我没接错（10 条断言 + 故障对照） |
| A05 | 扫码 + App | 移动端那两条特殊形状怎么写

但实际接入一个生态（这里就是 go-ah + mn-rt + fr 三件套）时，光走完 A 还会有几个**架构级问题**反复浮现：

1. **链路全景**——CLI 在哪一跳、App 在哪一跳、IdP 在哪一跳，三方拼起来完整流程长什么样？每个跳需要看哪个仓库的哪份代码？
2. **Provider 还是 RP**——一个服务**自己提供** OIDC（自当 IdP，例如 go-ah）与**作为依赖方接入别人的 IdP**（例如 mn-rt）是两种根本不同的形态。一个原本自管账号的服务什么时候该走出这一步、走出来之后生态链变成什么样？
3. **客户端模型**——注册一个 client 到底有哪些字段（client_id / scopes / redirect_uris / pkce_required / is_public）、哪些是 hard-coded、哪些走管理端、谁负责 seed、谁负责同构？同一个生态里的多个 client（mn-rt / fr-app / gs-ac）为什么必须分开而不是合并成一个？
4. **refresh_token 归属**——业务服务平台怎么"长期调用"业务接口？是用 refresh_token 静默续期，还是另发令牌？CLI / App 是不是替业务"桥"出了 refresh_token？这条最容易写错，先把假象拆了再讲设计。

这四个问题，A 不回答；它们要么跨多个接入实例（CLI + 服务端 + 移动端 + 认证中心），要么触及更深一层的架构选型。所以单列 B 序列。

## 加载时机

- **接一个新接入方之前**先读 B00→B01，弄清"我会接入到哪一跳、需要看哪个仓库的哪份代码"
- **设计服务自己当 IdP / 改造既有认证模块**时读 B02
- **注册 / 改造客户端注册逻辑**时读 B03
- **被问"refresh_token 怎么存 / CLI 是不是桥 / 业务后端怎么做长期调用"时**读 B04

A 与 B 的关系：A 是"动作层"（接入怎么做），B 是"结构层"（架构长什么样、为什么是这副样子）。接入动作里的代码片段在 A；这套代码片段在生态里处于哪个位置、为什么这么写，在 B。
