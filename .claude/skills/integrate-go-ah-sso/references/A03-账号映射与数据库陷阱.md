# A03 · 账号映射与数据库陷阱

> 加载时机：写身份落地之前**必读**。本 ref 的每条都在真实库上付出过代价。

## 映射表

```sql
CREATE TABLE IF NOT EXISTS user_identities (
    id            BIGSERIAL    PRIMARY KEY,
    user_id       BIGINT       NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    issuer        VARCHAR(255) NOT NULL,   -- 多认证中心并存时不串号
    subject       VARCHAR(255) NOT NULL,   -- id_token.sub
    email         VARCHAR(200) NOT NULL DEFAULT '',  -- 以下三列是快照，只排障
    username      VARCHAR(100) NOT NULL DEFAULT '',
    nickname      VARCHAR(100) NOT NULL DEFAULT '',
    last_login_at TIMESTAMPTZ,
    created_at    TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT NOW()
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_user_identities_issuer_subject
    ON user_identities (issuer, subject);
CREATE INDEX IF NOT EXISTS idx_user_identities_user ON user_identities (user_id);
```

- `user_id` 上**刻意不建唯一约束**：认证中心可能给两个外部身份断言同一个邮箱，
  此时它们共用同一个本地账号正是"邮箱优先"的预期。
- 快照三列每次登录刷新，但**业务判定一律读 `users` 表**，不要拿快照做逻辑。

## 判定：邮箱命中 > 既有绑定 > 建号

```go
identity    := 查 (issuer, subject) 的绑定   → boundUserId
emailUserId := 查 users.email = id_token.email → emailUserId

switch {
case emailUserId > 0 && emailUserId != boundUserId:
    if boundUserId > 0 { out.Rebound = true; 落 warning 日志(新旧 userId + 邮箱) }
    userId = emailUserId                       // 邮箱赢
case emailUserId == 0 && boundUserId > 0:
    userId = boundUserId                       // 没邮箱 / 本地邮箱已改 → 回退绑定
case emailUserId == 0 && boundUserId == 0:
    userId = provision(...)                    // 建号
}
// 绑定 upsert：user_id 跟随本次判定，快照与 last_login_at 每次刷新
```

**为什么邮箱优先**：接入统一登录的目标是"已经在认证中心有身份的人拿回他原有数据"。
若 `sub` 优先，一个先用邮箱密码注册、之后才在认证中心建号的人，首登会被自动建出一个空账号
并被 `sub` 永久绑住——老数据再也拿不到，功能等于白做。这是本次真实返工过一次的地方。

**代价要讲清楚**：以邮箱为主键 = "认证中心说这个邮箱是谁，谁就能拿到该邮箱的本地账号"。
前提是认证中心为本组织可信方、且它自己保证邮箱归属（注册走验证码）。补偿措施是改绑绝不静默：
`warning` 日志 + 响应 `rebound=true` + **被放弃的账号一行数据都不删**。

## 三条路径共同的落地要求

自动建号必须**复刻平台自己的完整注册流程**——个人工作空间、成员关系、回填默认组、
发自己的邀请码。只插一行 `users` 会造出"能登录、但所有按组归属的功能全部不可用"的账号，
比登录失败更难排查（用户以为坏了，其实是空的）。

接管既有账号时**只能新增、不能改写既有字段**：

| 字段 | 动作 | 原因 |
| --- | --- | --- |
| `users.email` | 永不覆盖 | 它就是外部身份主键，自动改等于自动搬账号；还会撞别人的唯一索引造成静默串号 |
| `users.nickname` | **仅当本地为空时**用认证中心的 `name` 补齐 | 无条件同步会冲掉用户自填昵称，而且"每次登录都同步"意味着这字段从此改不动 |
| `users.username` | 不动；新账号建号时撞车就写 NULL | 见下 |
| `users.password` | 不动 | 接管型账号保留密码登录能力；纯 SSO 建号的账号留空串，走密码登录会被拒（无绕过风险） |

整段判定放在**一个事务**里。并发首登时 `uq_user_identities_issuer_subject` 是最后兜底：
真撞了就整体回滚抛错，而不是出现两条绑定指向不同人。

## 数据库五个真实陷阱

### 1. 部分唯一索引 + 空串

```sql
CREATE UNIQUE INDEX uq_users_email ON users (email) WHERE email IS NOT NULL;
```

`WHERE ... IS NOT NULL` 意味着**空串照样受唯一约束**。所以"没有邮箱"必须写 NULL：

```go
var email any
if in.Email != "" { email = in.Email }   // 传 nil → 插 NULL
```

写 `''` 的后果：第一个无邮箱用户能建，第二个直接唯一冲突，报错还看起来像"邮箱重复"。
同一逻辑反过来用在 `username` 上：它是**全表唯一索引**（非部分），所以本地老数据占了名是
常态（历史上 username 存的就是邮箱），撞了要退回 NULL——PG 唯一索引不约束 NULL。

### 2. 自增序列落后于显式插入的 id

测试/迁移脚本用 `INSERT ... (id) VALUES (9501)` 显式塞 id，**序列不会前进**。后果有两层：

- 序列从 78 一直往上发，爬到 9501 时开始撞唯一约束——注册和自动建号会突然批量失败
- 更要命的是**id 回收**：序列发出的小 id 是几个月前被删用户的 id，而那些被删用户留下的
  关联数据还在（见陷阱 3），于是新账号"继承"了陌生人的工作空间和数据

发现与修复：

```sql
-- 诊断：逐表比较序列当前值与 max(id)
SELECT last_value FROM public.users_id_seq;
SELECT max(id) FROM public.users;
-- 修复（纯元数据操作，不碰任何数据行；生产上先征得同意）
SELECT setval('public.users_id_seq',     (SELECT max(id) FROM public.users),     true);
SELECT setval('public.user_groups_id_seq',(SELECT max(id) FROM public.user_groups), true);
```

`user_groups` 这类表同样要查——只要它有历史显式 id。另外注意 `nextval` **不参与事务回滚**，
跑一轮回滚型测试也会把序列往前推（本次实测 65 → 77），别以为没落数据序列就不动。

### 3. `CREATE TABLE IF NOT EXISTS` 会静默跳过约束

迁移文件里写了 `owner_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE`，
**不等于线上真有这个外键**：如果表早以别的形态存在，整条 `CREATE TABLE` 被 IF NOT EXISTS
跳过，外键从未建立。后果是"删用户会连带清掉工作空间"这个假设不成立。实测：

```sql
SELECT conname, pg_get_constraintdef(oid) FROM pg_constraint
 WHERE conrelid='public.user_groups'::regclass AND contype='f';   -- 结果可能是空
SELECT count(*) FROM public.user_groups g
  LEFT JOIN public.users u ON u.id=g.owner_id WHERE u.id IS NULL; -- 孤儿行数
```

**规则：凡是依赖 FK / 唯一索引 / 默认值的行为，上线前用 `pg_constraint`、`pg_indexes`、
`information_schema.columns` 实测，不要读迁移文件推断。**

### 4. 同名表跨 schema

一个 PG 实例上多个平台各占一个 schema（`auth_hub`、`public`、历史遗留 demo schema…），
`users` 这类表名会撞。查 `information_schema.columns` 不带 `table_schema` 过滤时，
返回的是**多张同名表混在一起的列**——看起来像"这张表有 20 个诡异列"。

同理，用代码生成器（`gf gen dao`）时它会跨 schema 合并同名表的列，把 entity 污染掉。
安全做法：只给要生成的表名、且确认全库唯一：

```bash
gf gen dao -l "<连接串>" -t user_identities     # 用 -t 限定单表，别走全量配置
git status --short                               # 只应新增 4 个文件，不得有既有文件被改
```

### 5. 在共享/生产库上跑测试

旧惯例"插入测试数据 + `t.Cleanup` 里 DELETE"在这种库上是**删生产数据**——本次就发现既有
集成测试会 `DELETE FROM users WHERE id=9701`，而那是个带邮箱的真实账号。

正确范式：**跑在必定回滚的外层事务里，不落数据、不做任何 DELETE**，并且不靠"相信框架"：

```go
var errRollbackOnly = errors.New("强制回滚，测试不落库")

func runRollbackOnly(t *testing.T, f func(ctx context.Context) error) {
    var inner error
    err := g.DB().Transaction(gctx.New(), func(ctx context.Context, tx gdb.TX) error {
        inner = f(ctx)
        return errRollbackOnly        // 无论 f 结果如何都以 error 收尾 → 回滚
    })
    if inner != nil { t.Fatalf("用例主体失败: %v", inner) }
    if !errors.Is(err, errRollbackOnly) {
        t.Fatal("外层事务没有按预期回滚 —— 测试可能真的写了库")
    }
}
```

能这么做的原因是 GoFrame 默认事务传播是 `PropagationRequired`：嵌套时**直接复用 ctx 上已有的
事务**（`gdb_core_transaction.go`），所以被测代码内部那个 `Transaction` 不会自己 commit。
换个框架或用 `RequiresNew` 这层保护就失效——所以每组分完还要**用一个不在事务里的独立连接
复查残留**：

```go
n, _ := dao.UserIdentities.Ctx(gctx.New()).Where("subject like ?", "sub-"+tag+"%").Count()
if n != 0 { t.Errorf("有 %d 行落库了，测试应当只回滚", n) }
```

再用第二个客户端（sql-harness 之类）从外部复核一次总行数，才算闭环。
