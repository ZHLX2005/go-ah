# A02 · 业务侧代码骨架

> 加载时机：阶段 2、3 动手前。

## 分层：协议与身份绝不混在一个文件

```
internal/service/oidc/     只懂协议：发现文档、code 换 token、验 id_token 签名
internal/service/<user>/   只懂归属：外部身份 → 本地哪个账号、建号、签发本系统凭据
api/<x>/v1/                DTO（含 g.Meta 路由标签）
internal/controller/       只做 DTO 搬运，不写业务
```

为什么这样切：验签这件事有标准库能干（`coreos/go-oidc`），归属判定是本地业务知识；混在一起
时，"改判定顺序"和"换 SDK"会变成同一坨改动，回归面失控。

**协议层不要自己解 JWT**。签名（RS256+JWKS）、`iss`、`aud`、`exp` 全部交给 SDK：

```go
idToken, err := verifier.Verify(exCtx, rawIDToken)   // 校验不过直接 error
// go-oidc v3 的 IDToken 上 Issuer / Subject 是**字段不是方法**（v2 习惯写 idToken.Issuer()
// 会编译失败：cannot call ... string is not a function）。
// 只补 SDK 不认识的三个 OIDC 标准 claim：
var claims struct {
    Name              string `json:"name"`
    PreferredUsername string `json:"preferred_username"`
    Email             string `json:"email"`
}
err = idToken.Claims(&claims)
```

## 配置：一块 YAML + 一套环境变量覆盖

```yaml
oidc:
  enabled: true
  issuer: "http://auth.example.com:8082"   # 与认证中心 IDP_ISSUER 逐字一致（含 scheme/端口）
  clientId: "my-platform"
  clientSecret: ""                         # 公共客户端 + 强制 PKCE，留空
  redirectUri: "https://app.example.com/oidc/callback"
  scopes: "openid profile email"
  httpTimeoutSeconds: 10
```

覆盖规则做成 `<PREFIX>_OIDC_<大写下划线>`，并且**显式 `os.Getenv`**，别指望配置库自动映射
环境变量（多数配置的 env 映射只覆盖少量键，静默失效最难查）：

```go
func confStr(ctx context.Context, key, def string) string {
    if v := os.Getenv(envPrefix + upperSnake(key)); v != "" { return v }
    return g.Cfg().MustGet(ctx, "oidc."+key, def).String()
}
```

三条纪律：

- 凭据与真实域名只走 env 注入，**不进 git 的配置文件**（配置文件里放可用的本地默认值可以）
- `enabled=false` 时接口必须短路返回、完全不碰网络
- `upperSnake` 这种小工具要单独写表驱动测试：`clientId→CLIENT_ID`、`httpTimeoutSeconds→HTTP_TIMEOUT_SECONDS`

## provider 自举：只有成功才固化

```go
func setup(ctx context.Context, cfg ClientConfig) error {
    mu.Lock(); defer mu.Unlock()
    if provider != nil { return nil }                    // 成功才走这条快速路径
    base := gooidc.ClientContext(ctx, &http.Client{Timeout: timeout})
    base = gooidc.InsecureIssuerURLContext(base, cfg.Issuer)   // issuer 是 http，必须显式放行
    p, err := gooidc.NewProvider(base, cfg.Issuer)
    if err != nil { return err }                         // 失败不缓存 → 下次请求可重试
    provider, verifier = p, p.Verifier(&gooidc.Config{ClientID: cfg.ClientID})
    oauth2Cfg = &oauth2.Config{ClientID: cfg.ClientID, RedirectURL: cfg.RedirectURI,
                               Endpoint: p.Endpoint(), Scopes: cfg.Scopes}
    return nil
}
```

**为什么不用 `sync.Once`**：容器编排下业务服务先于认证中心启动是常态。`Once` 会把"第一次失败"
永久记住，之后每次登录都返回同一个错误，直到人工重启——单点登录就这样一直不可用。

## 换 token 的四个细节

```go
// 1) 先验参数再连网。顺序反了的话，"忘传 code_verifier"会先表现成一次认证中心超时，
//    把真正的原因盖住。
if strings.TrimSpace(in.Code) == "" || strings.TrimSpace(in.CodeVerifier) == "" { … }

// 2) 复制一份再改。oauth2Cfg 是进程级共享的，直接改 RedirectURL 会被并发登录互踩。
c := *oauthCfg
if in.RedirectURI != "" { c.RedirectURL = in.RedirectURI }

// 3) verifier 是 PKCE 的唯一凭据，必须显式带上
tk, err := c.Exchange(exCtx, in.Code, oauth2.SetAuthURLParam("code_verifier", in.CodeVerifier))

// 4) 授权响应里没有 id_token 是合法 OIDC 但不可用于登录 → 明确报错，不要退回用 access_token
raw, ok := tk.Extra("id_token").(string)
```

`redirect_uri` 在授权请求里用了什么，换 token 时必须**原样**带上，两边不一致认证中心直接拒。
所以 callback 入参要能接收它，而不是硬用配置值（本地回环端口随机时尤其需要）。

## 会话与续期：refresh_token 一律不落地

**规则**：拿到令牌响应之后，`refresh_token` 就地丢弃。不落浏览器存储、不落客户端本地文件
或键盘、后端自己的会话表也不存。业务侧只维持**自己签发的短会话凭据**，过期就重新发起一次
授权跳转。

三条理由，缺一不可地指向同一个结论：

1. **在 go-ah 这套部署里，refresh_token 是"谁拿到谁能用"的裸长期凭据。** 已实测：全部 5 个
   注册客户端 `is_public=true` 且 `client_secret` 为空；发现文档无 DPoP / mTLS /
   sender-constraint 能力，代码里也搜不到这类校验。于是这串字符只要离开进程，7 天内可无限
   换新凭据，而认证中心**没有**"换 token 时再验一次调用方身份"这道锁。加密存储只让库里的
   字节不可读，挡不住应用层能读到的任何一条路径（SSRF、模板注入、备份外泄、日志、误连生产）。
2. **静默续期会让"统一登录"这件事名存实亡。** 续期 + 会话滑动延长组合起来，用户
   **永远不会再回到认证中心**：统一登出的可感知性、周期性重新确认身份、认证策略变更的
   生效时机，全部被这套机制绕开。
3. **泄露窗口从 10 分钟被拉长到 7 天。** `access_token` 只有 10 分钟；缓存 refresh_token
   等于把"一次凭据泄露"变成"一周可持续获取新凭据"。

> **不要把理由 1 读成"协议禁止服务端存 refresh_token"——这不是协议立场。**
> RFC 9700 与 OAuth 2.0 for Browser-Based Apps 的硬约束是**不要把 refresh token 暴露给
> 浏览器端 / 设备端**；机密客户端在服务端持久化 refresh token 是业界通行做法（BFF 模式，
> Keycloak / Auth0 的示例都这么做），而且 OAuth 术语里的 "client" 本来就包含它的后端。
> 服务端持久化**唯一可辩护的前提**是那把 token 单独拿到换不出东西：要么客户端是有 secret
> 的机密客户端**且** token 端点真的校验它，要么凭据是 sender-constrained（DPoP / mTLS）。
> go-ah 两条都不提供，所以本平台的规则才落到"客户端和服务端都不存"。
>
> **理由 2 与存储位置、与机密/公共身份都无关，独立成立**——哪天真配了 secret 或上了 DPoP，
> 理由 1 会减弱，但"不要用后台静默续期把用户永远挡在认证中心之外"这条不变。
>
> 分层记住：① 任何情况都不进浏览器/设备本地存储（协议硬约束）；② 服务端能不能存，
> 取决于凭据是否被 secret 或 sender-constraint 锁住（本平台=不能）；③ 无论存哪都不要自动续期。

### 各时限的真实数值（改代码前先看这张表）

| 东西 | 时长 | 出处 | 谁决定"多久要回一次认证中心" |
| --- | --- | --- | --- |
| 授权码 `code` | 5 分钟、一次性 | `auth-hub/internal/consts` | — |
| `access_token` | 10 分钟 | 同上 | 否 |
| `id_token` | 1 小时 | 同上 | 否 |
| `refresh_token` | 7 天 | 同上 | **不该被客户端持有** |
| 认证中心全局会话 `idp_session` | 30 天 | 同上 `SessionTTL` | **是**：30 天内重新授权是无感跳转（活跃用户看门狗自动续期） |
| 业务平台自己的会话 | 自己定 | 模板 8h 滑动 / dev_ctr_hello JWT 30 天 | 否，但决定用户体验节奏 |

"过几个小时要重新登录"这件事该由**业务会话 TTL** 控制，而不是靠持有 refresh_token 去回避。
把业务会话设成 8h/12h 随需求，到期重新 302 一次即可。

### bad_eg：这两条都是错的方向（模板里就是第一条）

```go
// ❌ 后端把 refresh_token 存进会话表，并跑后台静默续期 + 滑动会话
sess.RefreshToken = enc(refreshToken)          // 会话表里长期存有 7 天凭据
for { if time.Until(sess.AccessTokenExpiresAt) <= 2*time.Minute { renew(sess) } }
sess.ExpiresAt = now.Add(SessionLifetime)      // 每次续期都往后推 → 用户永不回到认证中心
```

```js
// ❌ 前端更糟：整份令牌塞进浏览器持久化存储
localStorage.setItem('rt', data.refresh_token)   // XSS / 设备共享 / 备份都会把它带走
```

根因是同一个：把"用户不必重新登录"当成了必须达成的目标，于是用长期凭据去换它。
但代价是认证中心失去了对会话的实际控制权——它设计的统一登出、吊销、策略生效都指望
用户会回到自己面前。

### good_eg：过期就重新走授权，用户其实无感

```go
// ✅ 协议层：换到令牌后只取用需要的，refresh_token 不进入任何持久化结构
tk, err := c.Exchange(exCtx, code, oauth2.SetAuthURLParam("code_verifier", verifier))
rawID, _ := tk.Extra("id_token").(string)
idToken, err := verifier.Verify(exCtx, rawID)
// 到此为止。tk.RefreshToken 不写库、不入会话、不进响应体、不打日志。

// ✅ 业务侧：只签发自己的短会话凭据（本项目就是继续签自己那套 JWT）
//    会话到期 → 前端发现 401 → 重新发起 /oauth2/auth
//    idp_session 还在（30 天内，活跃滑动）→ 认证中心直接 302 回带 code，不要求输密码
```

要点：`/oauth2/auth` 在认证中心**已有会话**时不会让用户重新输密码，只会走一次授权确认
（同一 client + 同一 scope 通常可静默放行）。所以"回到登录页重新拿"的实际体验是一次页面
跳转，而不是重新登录。把这件事当成体验代价而回避掉，是不必要的。

三条实现约束：

- 换 token 的响应**只解析需要的字段**，`refresh_token` 不进入任何会被序列化出去的结构体；
  对外接口响应体里也不要有它。
- 日志脱敏要覆盖到：确认 `refresh_token` 不会因打印整个响应体而进日志文件。
- 如果确实需要"长时间不掉线"，正确做法是**延长业务自己的会话**并在到期时重新授权，
  而不是持有 refresh_token。

### ⚠️ 与本仓库自带模板的冲突（事实层标注）

`template-business-server` 当前的做法与上面这条规范**相反**，且不是笔误而是有意设计：

| 位置 | 现状 |
| --- | --- |
| `template-business-server/api/store.go` | `refresh_token` AES-256-GCM 加密后写入 `business_sessions` |
| `template-business-server/api/refresh.go` | 后台 `Refresher` 每 30s 扫描，access_token 剩 <2min 就自动续期 |
| `template-business-server/api/refresh.go` | 续期时 `ExpiresAt = now + SessionLifetime`，会话滑动延长 |

也就是说：**照抄模板 = 违背本规范**。模板那套的价值在于演示"服务端如何安全地持有令牌"，
但"该不该持有"这一层它给的是否定的答案。接入方请以本节为准；模板侧要不要改是另一个决定
（记在 SKILL.md 的错误案例里，别默认它是最佳实践）。

一个容易被误用来为模板辩护的事实：认证中心 `session.Destroy` 确实会"吊销该用户全部
refresh_token、清空 access_token"（`auth-hub/internal/logic/session/session.go:69`）。
但这**只发生在销毁全局会话时**——日常的业务会话过期不会触发它，所以客户端持有
refresh_token 的泄露窗口并不会因此缩短。

## 后端不做的事，写清楚为什么

| 不做 | 理由 |
| --- | --- |
| 不发起 302 跳转 | 纯 API 服务，跳转由调用方做；后端一旦存 state 就要引入会话或内存表 |
| 不校验 `state` | `state` 只有发起方自己存过才校验得了，后端无从校验 |
| 不用 `nonce` | `id_token` 是后端直连 token 端点换来的，不经过浏览器转手，没有注入窗口 |
| 不下发 `client_secret` | 公共客户端本就没有；即使将来换成机密客户端也不能给浏览器 |

这几条要写在包注释里。不写，下一个接手的人会以为你漏了防护。

## 没有前端时，谁做浏览器侧那一步

纯 JSON API 接入 SSO 会有一个空档：授权完浏览器要落在某个页面才能把 `code` 交给后端。
随包发布一个最小参考页（放在服务自己的静态目录下，兼作可点验证入口与"活文档"）。

**http 明文环境的硬约束**：`crypto.subtle` 只在 secure context（https 或 localhost）可用，
`http://内网IP:端口` 下它是 `undefined`，标准 PKCE 写法直接跑不起来。
而 `crypto.getRandomValues` **不受此限制**。所以：随机数用原生，SHA-256 自带一份。

自带实现必须这样验，否则一个 hex 位的抄错你要查到天荒地老：

- 与 Node `crypto.createHash('sha256')` 对拍，覆盖**填充边界**长度（55/56/63/64/65 字节）、
  多块（>128）、UTF-8 多字节字符
- 再用 BigInt **从素数的平方根/立方根独立重推** K/H 两张魔数表——摘要对不上只能告诉你
  "结果错了"，独立推导才能定位到 `K[51]` 是哪一位

本次实测就抓出 `K[51]` 手抄成 `0x34b0bcb1`（正确 `0x34b0bcb5`），人眼扫表完全看不出。

另外两个页面侧的坑：

- 拿到 token 后清地址栏的 `?code=` 用 `history.replaceState`，**不要用 `location.replace`**——
  后者触发整页导航，会把刚渲染的登录结果冲掉（token 只存在内存里，一导航就没了）
- 不把 JWT 写进 `sessionStorage`：本方案前提就是 token 不长期留在浏览器

## 第三种形态：原生 App 自己跑完浏览器那一步

上面那节解决的是"纯 JSON API + 有浏览器可用"。原生 App 是另一种情况：
**没有浏览器 UI，但设备就是自己的**。做法是用 HTTP 客户端把
`authorize → consent → code` 这一段程序化跑完，再把 `code + code_verifier`
交给业务后端已有的 `/user/oidc/callback`。

分工因此变成：App 负责"证明这台设备已登录"，后端负责"据此领自己的 token"。
认证中心侧**零改动**。凭据模型与为什么不存 token，见 [[A05-扫码登录与移动端批准]]。

**三个必须踩中过的 HTTP 陷阱**（都是"看着成功、其实断了"类型）：

1. **默认客户端会自动跟随 302。** `http.Client` 就是如此 —— 于是 `authorize` 拿回来的是
   consent 页面的 200 HTML，`Location` 里的授权参数被整个吞掉，症状是一个看不出根因的
   `authorize_unexpected_status: http 200`。而 `followRedirects` 挂在
   **HttpClientRequest** 上、`package:http` 不暴露那个对象，所以只能自己实现 `send()`。
2. **多条 `set-cookie` 要显式拼好。** `dart:io` 的 `HttpHeaders` 没有 `addAll`/`.map`，
   要 `set()` 逐条写、`forEach()` 读；多条 `set-cookie` 必须用换行拼接并与解析端配对 ——
   拼成 `"; "` 或只取第一条，就会漏掉登录态那条，症状是"登录成功但未获得会话凭据"。
3. **chunked 响应的 `contentLength` 是 -1**，而 `http.BaseResponse` 拒绝负数。
   长度未知该传 null，不是 -1。

这三条 MockClient 一条都测不出来，因为它们错在"与服务端实际约定不符"。
原生流程必须有**打真实认证中心**的集成测试。

## 接口形状与错误处理

对外两个接口（都挂在既有的公开路由组上，与 `login` 同档位，不需要新开鉴权组）：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `…/oidc/config` | 下发 issuer / client_id / scopes / authorize 地址 / 登出地址 + `idpAvailable` |
| POST | `…/oidc/callback` | 入 `{code, codeVerifier, redirectUri?}`，出**与原密码登录同构**的凭据 |

出参与原登录接口同构（`token` + `userId`）是刻意的：已接入密码登录的客户端可以无痛切换。
额外只加排障字段：`sub` / `idpIssuer` / `provisioned` / `identityBound` / `rebound`。

- 错误一律走框架统一信封（`code != 0` + `message`），与既有登录失败保持同一形状；
  别为了"更 REST"单独给这个接口造 503，前端要写两套判断。
- `idpAvailable=false` 时仍返回**按 issuer 拼出来的兜底端点**：让失败发生在认证中心的登录页，
  而不是"配置缺失"这条更难排查的路径上。
- 代价要写进注释：该接口会同步尝试连认证中心，中心不可达时最坏慢一个超时时间。
- 日志里只打 `sub` / `userId` / 标志位，绝不打 token。确认日志脱敏中间件仍覆盖 `Authorization`。

## 依赖引入

```bash
go get github.com/coreos/go-oidc/v3      # + golang.org/x/oauth2
go mod tidy
```

`go mod tidy` 不能省：只 `go get` 时新依赖会留在 `// indirect` 注释里，且可能捎带无关版本。
之后**用 CI 等价的方式验一次**：

```bash
go build -mod=readonly ./...   # 只读模式下还能构建，才说明 go.mod/go.sum 是自洽的
```

否则会出现本地能编、CI 因 `-mod=readonly` 报 "updates to go.mod needed" 的经典尴尬。
