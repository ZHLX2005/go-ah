# B03 · 客户端注册方式

> 一个 client（RP / 业务后端 / CLI / App）在 go-ah 这个 IdP 眼里到底长什么样？哪些字段必填、哪些字段决定了行为差异、谁负责注册、注册之后能不能改？

## 加载时机

- 给 IdP 注册一个新接入方（CLI、新 App、新业务后端）
- 评估"内置 client"该不该加、加到哪个仓库、加几条 redirect_uri
- 看某个 client 的当前生效配置（排查"为什么 400 redirect_uri 未在白名单内"）
- 决定一个新的 client 该 public 还是 confidential、要不要 PKCE

## 字段全表

| 字段 | 含义 | 取值 | 证据 |
|---|---|---|---|
| `client_id` | 全局唯一字符串标识 | 字符串；本平台 seed：`template-web-client` / `gs-ac` / `oidc-cli` / `mn-rt` / `fr-app` | `auth-hub/internal/consts/consts.go:227-237`（ClientMnRT 注释完整） |
| `client_name` | 给人看的名字 | 字符串 | POST `/api/admin/clients` body；manage UI 渲染 |
| `redirect_uris` | 允许的回调地址白名单 | 字符串数组；存储是空格分隔的单字符串，API 收数组；精确到 path；loopback 主机允许端口通配 | `auth-hub/internal/logic/oidc/oidc.go:170-187`（ValidRedirectURIs）；`db/ddl/schema.sql` |
| `scopes` | 该 client 被允许请求的 scopes | 字符串数组（`openid` / `profile` / `email` / 业务自定义） | 同上 body |
| `is_public` | 是否公共客户端 | `*bool`；**不传 = true** | A01 / 同 body |
| `pkce_required` | 是否强制 PKCE | `*bool`；**不传 = true** | 同上 |
| `enabled` | 是否启用 | `*bool` | 同上 |
| `post_logout_uris` | RP-initiated logout 回跳白名单 | 字符串数组；只接受精确匹配、不通配 | A01 |
| `has_secret_or_empty` | 是否配过 secret（不出明文，只返标志位） | bool | `AdminClientView` 字段 |

### 选型判据

| 场景 | is_public | pkce_required | secret |
|---|---|---|---|
| 后端 Web 应用（自家服务端、有静态部署） | false | true（推荐） | 推荐配（机密客户端） |
| SPA / 静态站点（仅有浏览器、无法藏密钥） | true | true | 无 |
| CLI / 原生 App | true | true | 无 |
| H5 / 内嵌 WebView 的 App | true | true | 无 |
| 自家后端互相调用（service-to-service） | false | true | 配且不放前端 |

**go-ah 的现实约束**（关键：A02 第一条）：

> 5 个内置客户端都是 public 且无 secret；token 端点读了 client_id（form → query → Basic）但**从不校验 secret**；PKCE 是唯一凭据。

也就是说，**所有本平台内的 RP 都走 public + PKCE**，配 secret 反而误导（"看起来加密了"）——本平台没配 DPoP / mTLS，配 secret 不提供任何额外安全性。详见 A02。

## 谁负责注册：本平台的现实

go-ah 当前**只支持两种注册来源**：

1. **内置 seed**（代码级常量，部署即在）——在 `auth-hub/internal/consts/consts.go` 里以常量形式定义 `client_id`；部署时 `auth-hub/internal/db/db.go` 的 seed 逻辑把它们写进 `o_auth_clients` 表
2. **管理端 API** `POST /api/admin/clients`（运行时添加）——需要管理员登录后才能调用，body 字段 snake_case

**不支持**：
- 动态自注册（RFC 7592 DCR）——本平台客户端清单是受控的，"谁来注册"没说清楚之前不会放
- 自动签名 secret 后返回明文（仅一次）——机密客户端的能力；本平台未启用

### 内置 seed 清单

| client_id | 类型 | 用途 | 注册处 |
|---|---|---|---|
| `template-web-client` | 公私皆可（模板） | 脚手架模板 | 同 consts.go / db.go |
| `gs-ac` | 公共 + PKCE | 集团 AC；其 redirect_uris 在每次启动时由环境变量重新同步进库 | consts.go / db.go（GSAC 注释特别说明 env 重同步） |
| `oidc-cli` | 公共 + PKCE | CLI 模板（template-oidc-cli 引用） | consts.go |
| `mn-rt` | 公共 + PKCE | 远程输入桥 PC CLI；redirect_uri `http://127.0.0.1:*/callback` 与 `http://localhost:*/callback` | consts.go:227-237（ClientMnRT 注释） |
| `fr-app` | 公共 + PKCE | Flutter App；同样 loopback 通配 | consts.go（ClientFRApp 注释） |

`presetClientIDs` 与"是否都就位""种子幂等后的行数"两处断言共用同一份来源（`db_integration_test.go`）——**加内置客户端只改这一处**，硬编码的"5"也要一起改（详 A01 错误案例）。

### 为什么不用同一个 client_id

**审计与吊销的单位**。把 mn-rt 与 fr-app 合并成"客户端"=统一一个 id 后，"是哪个平台在发 token"、"要停掉哪条接入"都问不出来。A01 在 ClientMnRT 注释里明确写了这个理由：**别复用 oidc-cli**。

## 注册流程与硬判据（与 A01 一致，此处展开 file:line）

### Step 1 · 客户端 POST `/api/admin/clients`

字段形如：

```json
{
  "client_id": "my-platform",
  "client_name": "我的平台",
  "redirect_uris": ["https://app.example.com/oidc/callback",
                    "http://127.0.0.1:*/oidc/callback"],
  "scopes": ["openid", "profile", "email"],
  "is_public": true,
  "pkce_required": true,
  "enabled": true,
  "post_logout_uris": ["https://app.example.com/"]
}
```

要点（A01 已说尽，列 file:line 作锚）：

- 公共客户端不要 `client_secret`。token 端点读了 client_id 但从不校验 secret。
- `is_public` / `pkce_required` / `enabled` 都是 `*bool`，**不传等于 true**——别指望默认帮你关
- 非公共客户端会生成 `cs_<random>`，只在创建响应里明文返回一次；库里存明文（注释明确写"生产应存哈希"）

### Step 2 · `redirect_uris` 的匹配语义（最容易踩的）

存储是**空格分隔的单个字符串**，API 层收发数组。匹配规则（`auth-hub/internal/logic/oidc/oidc.go:170-187` + 客户端 `AllowsRedirect` 函数）：

- 默认**精确匹配，包含 path**。`http://host:8988/static/oidc-login.html` 与 `http://host:8988/oidc/callback` 是两个不同值；少写路径段直接 400
- **唯一例外**：loopback 通配 `http(s)://127.0.0.1:*/path` 与 `http(s)://localhost:*/path`——host 锁回环、**端口任意**、path 必须匹配（RFC 8252）。本地联调靠这条
- 未命中白名单 → **400，绝不回跳**（防开放重定向）
- `post_logout_uris` 只接受精确匹配，没有通配

注册时**一次把两类地址都写进去**：线上对外地址（精确）+ 本地回环（通配）。

### Step 3 · 不依赖管理端凭据的白名单探测

管理端凭据会被重置、也不该在脚本里落盘。验证 client 是否注册成功，用白名单探测法（A01 给的 probe 函数，证 4 件事：client 存在 / enabled / 白名单生效 / 拒绝逻辑生效）。这是**不需要管理端凭据的最强证据**。

```bash
probe() {   # $1 = redirect_uri
  curl -s -o /dev/null -D - -m 10 -G "$IDP/oauth2/auth" \
    --data-urlencode "response_type=code" \
    --data-urlencode "client_id=my-platform" \
    --data-urlencode "redirect_uri=$1" \
    --data-urlencode "scope=openid profile email" \
    --data-urlencode "state=x" \
    --data-urlencode "code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM" \
    --data-urlencode "code_challenge_method=S256"
}
probe "https://app.example.com/oidc/callback"   # 期望 302 → /login?return_to=…
probe "http://127.0.0.1:9999/oidc/callback"     # 期望 302（回环通配）
probe "https://evil.example.com/callback"       # 期望 400 未在白名单内
```

### Step 4 · 用 sql-harness 核对落库结果

```bash
sql-harness <<'PY'
use_workspace("<认证中心所在连接名>")
print(query("""SELECT id, client_id, client_name, is_public, pkce_required, enabled,
                     has_secret_or_empty, redirect_uris
              FROM auth_hub.o_auth_clients ORDER BY id"""))
PY
```

顺便确认一件容易忽略的事：认证中心与业务平台常常**共用一个 PG 实例、分处不同 schema**（`auth_hub` / `public`）。任何按表名查的操作都要带 schema，否则 `users` 这种同名表会命中错误的哪一张（本仓库就发生过：`auth_hub.users` 与 `public.users` 列完全不同）。

## 客户端行为差异：哪个字段决定什么

| 字段值变化 | 协议层差异 | 用户体验差异 |
|---|---|---|
| `is_public=false` 但不配 secret | 同上：token 端点不校验 secret，配了也无意义 | — |
| `pkce_required=false` | 客户端可省略 PKCE 参数；token 端点接受空 verifier | **极不建议**：在 IdP 没强制 PKCE 的情况下，"获取 code 即等同于获取 token"；一旦 code 落库或回跳被截，攻击者直接兑 token |
| `enabled=false` | authorize 阶段拒该 client_id（不在 DB / enabled=false 时不再走白名单匹配） | 该 client 下所有用户都进不去 |
| redirect_uri 不在白名单 | 400 `redirect_uri 未在客户端注册白名单内` | 用户看到 SSO 拒绝；没有任何"请向管理员添加"的入口（故意的——开放重定向防护） |
| `scopes` 不含 `openid` | authorize 阶段 302 带 `invalid_scope` | 同上 |
| `scopes` 不含 `email` | 用户能登录但 IdP 给不出邮箱 | 业务侧 A03 的"邮箱优先"判定拿不到邮箱，会走 sub 兜底（命中率低） |
