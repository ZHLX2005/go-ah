# A04 · 一次性验证与排错

> 加载时机：阶段 4；以及任何"登录不上"的排查。

## 三个层次，逐层加严

| 层次 | 证明什么 | 需要什么 |
| --- | --- | --- |
| L1 白名单探测 | client 注册生效、`enabled`、放行/拒绝逻辑都对 | 不需要任何凭据 |
| L2 服务端自举 | 业务服务**到**认证中心的服务端可达 + 配置正确 | 一个公开 GET |
| L3 完整链路 | 真人能登进来，且登进的是**他本人原有的账号** | 一个可用测试账号 |

L1+L2 就能在零凭据下把 90% 的配置错误挡掉。**L3 才是唯一能证明"接管对了"的一层**——
前两层全绿但身份判定顺序写反，是完全可能的（本次就发生了）。

## L1：不依赖管理端凭据探测注册

三条一组，第三条必须**失败**：

```bash
probe() { curl -s -o /dev/null -D - -G "$IDP/oauth2/auth" \
  --data-urlencode "response_type=code" --data-urlencode "client_id=$CID" \
  --data-urlencode "redirect_uri=$1" --data-urlencode "scope=openid profile email" \
  --data-urlencode "state=x" --data-urlencode "code_challenge=$CHAL" \
  --data-urlencode "code_challenge_method=S256" | grep -iE '^(HTTP/|location:)'; }

probe "$GOOD_ONLINE_URI"   # → 302  Location: /login?return_to=…
probe "$GOOD_LOOPBACK_URI" # → 302（回环通配）
probe "https://evil.example.com/cb"  # → 400 未在白名单内
```

全是 302 说明白名单没生效，比 400 更糟。

## L2：服务端自举判据

```bash
curl -s "$BIZ/…/oidc/config"
# 期望：enabled=true、idpAvailable=true、authorizationEndpoint 来自发现文档、
#       clientId 与注册值一致、**响应里没有任何 secret 字段**
```

`idpAvailable=false` 时先看 `idpError`：连不上=地址/防火墙；连得上但报错通常是 issuer 与
发现文档里的 `issuer` 不一致。

## L3：不用浏览器跑完授权码链路

关键点：认证中心的登录态就是 `idp_session` cookie，授权码由 **`POST /api/consent`** 签发。
所以纯命令行也能拿到真 code（这也是唯一能在无 GUI 环境下证明 PKCE 互操作正确的方式）：

```
1) POST  $IDP/api/login        {username, password}          → 存 set-cookie
2) GET   $IDP/oauth2/auth?...  (带 cookie, state + S256 challenge) → 302 到 /consent
3) POST  $IDP/api/consent      {client_id, redirect_uri, scope, state,
                                code_challenge, code_challenge_method,
                                decision:"allow"}            → {"redirect_to": "<cb>?code=…&state=…"}
4) 从 redirect_to 取 code（并断言 state 与发起时一致）
5) POST  $BIZ/…/oidc/callback  {code, codeVerifier, redirectUri} → 本系统凭据
6) GET   $BIZ/<某个受保护接口>  Authorization: Bearer <上一步凭据>
```

三条硬约束，写错任何一条都验不出真东西：

- **`code_verifier` 与 `code_challenge` 必须来自同一次 `obtainCode`**。如果为了构造"verifier
  不匹配"的负例而在两处各摇一次随机，两次 challenge 就对不上，你测的是"参数不一致"而不是
  PKCE。把 `effectiveChallenge` 算一次、复用。
- **`redirect_uri` 三处必须完全一致**：authorize、consent、以及业务侧换 token。
- 认证中心 `/api/consent` 返回**裸 `{"redirect_to"}`，没有 `{code,data}` 信封**；
  按信封取 `.data.redirect_to` 会得到 undefined，误判成"认证中心没发码"。

凭据一律从环境变量注入，脚本内不打印、不落盘、不写进任何提交。

## 十项验收断言

逐项全绿才算接完。**接管类断言（5、6）缺失是最常见的"看起来成功了"**：

1. `GET /health` 200，且启动时间表明是新构建（不是老进程）
2. `…/oidc/config` 200 且 `idpAvailable=true`
3. 参考登录页与其 JS 资源可访问（随镜像发布的东西最容易漏打包）
4. 假 `code` → 不返回 5xx，且业务码非 0、`message` 指向 `invalid_grant "code 不存在"`
5. 真实登录 → **落到的 userId 是此人原有账号**，且 `provisioned=false`、`rebound=false`
6. 用返回的凭据调受保护接口 200，能读到他原有的业务数据（不是只看 200）
7. 同一 `code` 重放 → 被拒（`code 已被使用`）
8. 换错 `code_verifier` → 被拒（`PKCE 校验失败`）
9. 二次登录 → 同一 userId、`provisioned=false`、`identityBound=false`；库里账号数不变
10. 原有密码登录仍可用；无凭据访问受保护接口仍按原样 401
11. **全链路查不到 `refresh_token`**：callback 响应体里没有、浏览器存储里没有
    （`localStorage`/`sessionStorage`/IndexedDB 全翻一遍）、业务会话表相关列里没有、
    服务日志里没有。一条最省事的粗筛：
    `grep -rn "refresh_token\|RefreshToken" <业务日志目录> <前端构建产物>` 应当只出现在
    协议注释或 discovery 文档里，不该出现在任何数据写入点。
12. **过期路径可用**：把业务会话 TTL 临时调到很短（或等自然过期）后访问受保护接口拿到 401，
    然后重新发起一次授权——应在**不输密码**的前提下直接拿回登录态（证明靠的是认证中心
    30 天全局会话（活跃用户看门狗续期），而不是被删掉的 refresh_token）。这条不跑，等于没验证"去掉静默续期之后
    用户还能不能用"。

外加一条数据面复核（用 sql-harness 从**另一个客户端**独立查，不要用被测服务自己的接口）：
映射表只新增预期的行、`users` 总行数与带邮箱行数符合预期、没有任何测试标识残留。

## 排错对照表

| 症状 | 真因 | 怎么确认 |
| --- | --- | --- |
| 授权页 404 / 跳到后端端口 | issuer 填成后端端口，不是浏览器可达的对外地址 | `curl $ISSUER/login` 要 200；比对发现文档里的 `issuer` |
| `400 redirect_uri 未在客户端注册白名单内` | path 不精确（匹配是含路径的精确比较，只有回环允许端口通配） | 用 L1 探测逐个地址试 |
| 换 token `invalid_grant "code 不存在"` | code 用过或已过期（一次性） | 每次负例都要重新 `obtainCode` |
| 换 token `PKCE 校验失败` | `verifier` 与授权时的 `challenge` 不是同一次；或自带 SHA-256 算错 | 先跑 Node 对拍 + 魔数表独立推导 |
| `id_token 校验失败` | `aud` 不是本 `client_id`；或 issuer 改过但签名密钥/配置没对齐 | 解 JWT header 看 `iss`/`aud`/`kid` |
| `认证中心未返回 id_token` | `scope` 缺 `openid` | 看 `/oidc/config` 的 scopes |
| 页面里 `crypto.subtle` 是 undefined | 非 secure context（http 明文 + 非 localhost） | 见 A02 自带 SHA-256 |
| **登录成功但看不到自己的数据** | 身份判定按 `sub` 优先，把人导到了新建空账号 | 断言 5：查 `users.email` 命中的 userId 是否等于返回的 userId |
| 用户昵称每次登录被改回去 | 无条件同步昵称 | 只应在本地为空时补齐（A03 表） |
| 第二个无邮箱用户建不出来 | 空串撞 `WHERE email IS NOT NULL` 部分唯一索引 | 查 `users.email=''` 是否已存在 |
| 某天起注册/建号突然批量唯一冲突 | 自增序列追上历史显式 id | 比较 `last_value` 与 `max(id)`（A03 陷阱 2） |
| 新账号里冒出陌生工作空间 | id 回收 + 被删用户的孤儿数据没清（外键根本没生效） | `pg_constraint` + 孤儿行统计 |
| 本地全绿、线上接口 404 | 没部署 / 镜像里没带上新配置（部署挂了宿主机旧配置） | 比对 `/health` 启动时间与容器内配置来源 |
| 本地能编、CI 报 `updates to go.mod needed` | 没 `go mod tidy`，新依赖停在 `// indirect` | `go build -mod=readonly ./...` |

## 验收报告应包含

一次接入交付时给出：三层的实际命令与输出摘要、十项断言的逐条结果（PASS/FAIL 原文）、
数据面前后对比（总行数 / 带邮箱行数 / 映射表新增行）、以及**明确列出哪些验证没做及原因**
（例如"未做真人登录：无可用的认证中心测试账号"）。把"没验的东西"藏起来，是这类接入
最贵的失误。

## 安全红线

- 线上/共享库上**不执行任何 DELETE 清理**；测试一律走"必定回滚 + 独立复查"（A03 陷阱 5）
- 不清理带邮箱的用户及其数据，即便看起来是测试残留——先问
- 明文凭据只走 env 注入，不进配置文件、不进脚本、不进提交、不进记忆
- Windows 下 curl 内联中文请求体会被编码破坏（远端存成 U+FFFD）：非 ASCII 一律
  `--data-binary @<UTF-8 文件>`
- 提交前 `git fetch` 看 ahead/behind；落后就先 rebase 整合，**绝不为"推上去"而 force push**；
  rebase 后核对 `git diff <remote> --stat` 必须是纯增量

## 验证本身的有效性（本节管"你怎么验"，不管"验什么"）

上面那些断言只有在**验证手段自己可信**时才有意义。下面五条全部是本轮真实付过代价的，
共同点是：验证显示通过，而功能其实是坏的。

### 1. 安全断言必须做负向对照

新加一条"某攻击必须被拒绝"的断言后，**临时移除被守卫的实现，确认它真的会变红**，
再恢复并复验。没有这一步，你不知道自己写的是守卫还是装饰。

```bash
# 拆掉防线 → 跑 → 必须 FAIL → 恢复 → 跑 → 必须 PASS
```

本轮三次靠它证明测试有效，也靠它暴露过一次"测错层位"的假绿（见下条）。

### 2. 测对层位：钉住请求 path，而不是只测响应解析

```dart
// ❌ 喂理想 payload 给 fromJson —— 端点 URL 写错它照样全绿
test('解析正确', () => QrPreview.fromJson(理想json));

// ✅ 用 MockClient 记录实际请求 URL，逐端断言"到底打了哪个 path"
expect(requested, ['POST /api/qr/sessions', 'GET /api/qr/sessions/$t',
                   'GET /api/qr/sessions/$t/preview', /* … */]);
```

真实事故：`preview()` 少写 `/preview` 后缀，打到了 PC 侧的**轮询**端点。那个端点
返回 200、`code=0`、结构合法，只是响应里**没有 `pc` 字段** → 设备画像全空 →
确认按钮被"画像缺失就不给确认"这条安全规则禁掉 → 扫码功能整体不可用，
而屏幕上没有任何一处报错指向真正的原因。第 1 类测试对这次事故完全无感。

### 3. 跳过不是通过

依赖外部服务的测试在目标不可达时 `return` 跳过（仓库既有口径），于是
**服务停掉之后那次「All tests passed」什么都没验证**。汇报时必须说清这次是真跑了还是空过；
需要强制时加一个 `REQUIRE_*=1` 让连不上直接判失败。

### 4. 管道会吞退出码

```bash
go build ./... 2>&1 | head -20 && echo "BUILD OK"   # ❌ head 成功就 OK，构建错误看不见
go build ./... && echo "BUILD OK"                    # ✅
```

本轮两次被这个假成功误导（一次是 Dart 文件、一次是 Go 包），
其中一次让我把"已格式化"的结论说成了事实。格式化同理：`gofmt -w` 之后若又编辑过该文件，
必须用 `gofmt -l`（**无输出**才算过）复验 —— CI 的 lint job 就查这个。

### 5. 部署成功不等于发布成功

CI job 绿了不代表线上是新的包。本轮的核对方式是把线上实际提供的字节拉下来对哈希：

```bash
curl -sL <分发地址> -o live.apk && sha256sum live.apk   # 与 CI 日志里的发布 sha256 比对
```

这不是过度谨慎：该工作流注释里就记着一次「job success 但线上还是旧包」的事故。
同理，本地验证通过不等于线上通过（阶段 5 判据）。

## 排错对照表（补充）

| 症状 | 根因 | 定位判据 |
|---|---|---|
| 确认页设备画像全空、确认按钮点不动，但无报错 | 手机侧端点打到了 PC 侧轮询端点（少 `/preview`） | 断言实际请求 path，而非响应解析 |
| 二维码刚出现就显示"0s 后失效" | 防探测把 `expires_in` 和 `status` 一起遮蔽了 | 无 `qr_ctx` 时 `expires_in` 必须是真实剩余秒数 |
| 原生流程 `authorize_unexpected_status: http 200` | HTTP 客户端自动跟随了 302，Location 被吞 | 用不跟重定向的客户端；断言拿到 3xx 与 Location |
| "登录成功但未获得会话凭据" | 多条 `set-cookie` 被拼成 `"; "` 或只取第一条 | 换行拼接，并与解析端按行拆分配对 |
