# B02 · 服务自提供（Provider 模式 vs 依赖方模式）

> 一个**原本自管账号**的服务（用户名密码注册、自己管 users 表）什么时候该自己提供 OIDC（变成 IdP / Provider），什么时候该作为依赖方接入别人的 IdP？go-ah 在本生态里属于哪一种？做出"自提供"决定之后，仓库结构、协议表面与生态链会变成什么样？

## 加载时机

- 评估新业务要不要自建 IdP / 把已有账号体系 OIDC 化
- 看 go-ah 在三件套里的角色（为什么它要专门起一个仓库）
- 给同事解释"为什么我们的服务都接到同一个中心，而不是每个服务自己一套账号"

## 两种形态一句话定义

| 形态 | 角色 | 表面 |
|---|---|---|
| **Provider（自提供）** | 颁发与管理身份，对外**自己就是一个 OIDC IdP** | `/.well-known/openid-configuration` / `/oauth2/auth` / `/oauth2/token` / `/oauth2/userinfo` / `/oauth2/jwks`；管理端 `/api/admin/clients`、`/api/consent` 等 |
| **依赖方（RP / Relying Party）** | **不颁发**身份，只**消费**别人的 token 来识别用户 | `/auth/oidc/config`（公参）；`/auth/verify`（接 token 换本服务的凭据）；`/auth/oidc/callback`（收授权码） |

一句话：**Provider 是 IdP；RP 是 IdP 的客户**。两种形态可以**同时存在于同一生态**——go-ah 是 Provider，mn-rt 和 fr 都是 RP。

## 走出"自提供"的判定信号

满足以下**任意一条**就该考虑自提供：

1. **同质多业务**——一个团队/公司有 ≥2 个业务后端，各自维护自己的"用户表+密码"；都让用户注册一次，重复建设
2. **跨服务身份该一致**——产品上希望"用户在一个应用里看到的所有账号归属与另一应用里的完全一致"（企业内、统一集团、客户+商家一体化）
3. **存在跨业务授权动作**——业务 A 的"扫码登录"让用户用同一身份登录业务 B 的客户端；这是 OIDC 的原生能力，自提供后两端自然继承
4. **需要统一登出 / 全局会话管理**——一处吊销、全生态失效；多 RP 体系下 IdP 拿到一次会话就能让用户在 RP 之间无缝切换
5. **存在跨业务管理员操作**——管理后台在多个后端之间做用户归属校验、设备吊销、审计

至少 1 条命中且当前身份系统已经"在 ≥2 个地方被用户复制粘贴过"，就该考虑自提供。

## go-ah 在本生态里的角色：纯 Provider

`go-ah` 的代码组织方式极清晰地印证它**只当 IdP**：

| 证据 | 位置 | 含义 |
|---|---|---|
| 全 Go + goframe 框架；入口 `auth-hub/` | `D:\code\a_go\proj\go-ah\auth-hub\` | 它是独立服务，不是 mass-incorporation 进某个业务 |
| 完整暴露 OIDC 八个端点 | `auth-hub/internal/controller/oidc/oidc.go` / `controller/auth/` / `controller/qr/` | Provider 标配：`/oauth2/{auth,token,userinfo,jwks,logout,revoke}` + `/api/consent` + `/api/qr/*` |
| 自带管理端 | `auth-hub/internal/controller/admin/`、`/api/admin/clients` | Provider 必须有；RP 不需要 |
| 自己维护 `users` / `user_sessions` / `o_auth_clients` / `qr_login_sessions` 等 | `auth-hub/internal/db/ddl/schema.sql` | 完整身份库 |
| 没有自己的"业务接口"（没有 `/api/products` 之类的） | 仓库只看到 auth-* / oauth2-* / admin-* | 印证"不做业务、只做身份" |
| `o_auth_clients` 表里有 5 个内置 seed（template-web-client / gs-ac / oidc-cli / mn-rt / fr-app） | `auth-hub/internal/consts/consts.go:227-237`、`auth-hub/internal/db/db.go` | Provider 的内置 RP 清单；纯 RP 仓库不会自维护 |
| RS256 自签 ID Token / JWKS | `auth-hub/internal/utility/jwk*.go` | Provider 必须能签 ID Token；RP 不签 |

## mn-rt 走这条路：纯依赖方

| 证据 | 位置 | 含义 |
|---|---|---|
| 监听 `wss://.../ws` + 自己的 HTTP（`/auth/oidc/config` 等） | `server/src/server.js:210-329` | 它是业务中转 + 一个 OAuth 客户端 |
| **`/auth/oidc/config` 是只读公共参数**，**不签 JWT、不颁发 token** | `server/src/auth.js:81-96` | RP 标准做法 |
| **依赖 go-ah 才能获得属主** | `server/src/auth.js:136-203`（`exchange` / `verifyBearer` 调 IdP 的 `/oauth2/userinfo`） | 没有 IdP 这台机器就不知道"我是谁" |
| **自己签的是设备令牌**（HS256），不签 ID Token | `server/src/auth.js:213-249` | RP 业务令牌可以自签，但身份核心声明必须由 IdP 颁的 access_token / ID Token 承载 |
| 没有 users 表 | 没有 `server/src/users.*` 之类的文件 | 印证"不自管账号" |

注意 mn-rt 仍然**有自己的用户体系**（设备注册表 `devices.json`），但**这个体系不存密码、不存邮箱主键**，只存 clientId↔sub 映射与每机的 sessionKey。详见 B04（refresh_token）与 A03（账号映射）。

## 自提供的代价与不可逆点

决定自提供前**先把这两类代价列在 PR 描述里**：

1. **要持续维护一个全栈项目**
   - 至少要有一个会同时写 Go + 关系数据库 + 前端（自提供 IdP 通常还要配 SPA 管理后台）的团队成员值班
   - 协议升级压力：OIDC Core 1.0 的所有边界都要自己处理（state、PKCE、sub 跨账号绑、rebound、token 撤销、回环签名）
   - 漏洞面在 IdP 这层而不是业务层：一旦 IdP 出问题，全生态停摆

2. **数据归属判定在 IdP 这一跳**
   - IdP 一句话能骗就骗：所有 RP 信任的所有身份结论都来自 IdP 颁发的 token / sub
   - 必须有 **回环审计**：每个 RP 的属主结论都能在 IdP 这边查到一致的来源（`oauth_clients.client_id` ↔ userinfo.sub ↔ RP 的"我以为的属主"）

不可逆点：**一旦发出第一枚 access_token，回滚成本极高**——所有 RP 都依赖 IdP 给的 sub 与 email 派生属主；硬切换到另一个 IdP 等于重做 A03 的全部判定。

## 当**不**自提供

以下场景即便命中判定信号 1-5，也**先不要自提供**：

- 用户量 < 千级、维护一个 IdP 的工作量远超收益——**用一个 SaaS IdP**（Keycloak、Auth0、Authing）就行，不必自己造
- 已有身份来源是外部系统（如企业 SSO、学校账号体系）——**做 OIDC RP** 接入它就够了
- 多业务之间其实没强身份一致性诉求（各自登录、各自记忆）——加个"跳转账号"按钮比改架构便宜得多
- 安全合规要求"身份由第三方托管"——那就**不要自提供**

## 现有生态里 Provider / RP 的对照

| 实体 | 角色 | 仓库 / 路径 | 关键证据 |
|---|---|---|---|
| go-ah | **Provider** | `D:\code\a_go\proj\go-ah\auth-hub\` | 八个 OIDC 端点 + users/user_sessions 表 + 管理端 |
| mn-rt server | RP | `D:\code\a_rust\proj\mn-rt\server\` | `/auth/oidc/config` 公开参数；`/auth/verify` 接 token；不颁 ID Token |
| mn-rt CLI | RP 客户端（native） | `D:\code\a_rust\proj\mn-rt\client\` | loopback 收码 + PKCE 换 token + Bearer /auth/verify |
| fr App | RP 客户端（mobile + H5） | `D:\code\a_dart\prj\fr\lib\` | mintCodeForClient + POST /auth/oidc/callback |
| fr 内部 goframe 后端 | RP（HTTP） | `fr/lib/api/goframe/oidc/` | OAuth 客户端同 fr App；`mintBackendToken` 走同一套 mintCodeForClient |

注意**同一 IdP 之下可以有任意个 RP**；新增一个业务后端要做的事只是 A 序列全流程——不需要碰 go-ah 的代码。

## 自提供的代码组织清单（参照 go-ah 形态）

若新业务决定自提供 IdP，至少要建以下目录骨架（与 go-ah 对齐）：

```
<new-idp>/
  auth-hub/                          # 主包
    internal/
      consts/                        # 客户端名、TTL、错误码常量
        consts.go
      controller/
        auth/                        # /api/login, /api/me, /api/register, /api/logout
        oidc/                        # /oauth2/{auth,token,userinfo,logout,revoke}, /api/consent
        qr/                          # 扫码端点（可选，但 go-ah 选了，所以顺手提）
        admin/                       # /api/admin/clients 等管理端
      logic/
        oidc/                        # IssueAuthorizationCode / ConsumeAuthorizationCode / FindClient
        user/                        # Authenticate / ProvisionNew
        qr/                          # 状态机、四条条件 UPDATE
      db/
        ddl/schema.sql               # users / user_sessions / o_auth_clients / oauth_authorization_codes / qr_login_sessions
        db.go                        # preset client 种子
      limiter/                       # 建票 / 批准两个独立限流（详 A05）
      utility/
        useragent.go / jwk.go / ...
      router/                        # 路由注册
    api/
      auth/v1/                       # DTO（LoginReq/Res、ConsentReq/Res）
      oidc/v1/                       # DTO（Authorize、Token、Userinfo）
      qr/v1/                         # DTO（CreateTicket、Claim）
```

签发协议核心：discovery、auth、token、userinfo 四个端点走完后，**其他都是叠加面**（管理、扫码、refresh_token 颁发）。起步不必上扫码，但 `o_auth_clients` 表 + 公私 client 注册逻辑 + redirect_uri 白名单**必须**先做对——这两条是 A01 钉死的，A01 即"自提供起步"的硬清单。
