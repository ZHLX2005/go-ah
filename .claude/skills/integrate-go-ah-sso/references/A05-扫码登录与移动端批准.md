# A05 · 扫码登录与移动端批准

> 扫码登录是认证中心的**第二个能力面**，与"第三方平台接入授权码"正交：
> 前者是"一台设备证明身份，另一台设备批准"，后者是"一个依赖方认领身份"。
> 二者共用同一个登录态，但端点、状态机、安全模型完全不同，所以单独成 ref。

## 一句话模型

**扫码不是一种新的授权协议，而是"输密码"的替代动作。**

PC 仍走完全不变的标准流程 `/oauth2/auth → /login → /consent → 授权码 → PKCE 换 token`，
只是登录页多一个"手机扫码"Tab。手机批准后，服务端**在 PC 自己发起的 claim 请求上**
下发 `idp_session` 全局会话。

由此得到四个结果：手机端**不必是 OIDC 客户端**（不需要注册 `redirect_uri`）、
不新增 `grant_type`（`/oauth2/token` 与发现文档一字未改）、不需要 CORS
（两端都只与 issuer 同源通信）、业务方零改动。

## 八个端点与鉴权口径

| 端点 | 侧 | 凭据 | 说明 |
|---|---|---|---|
| `POST /api/qr/sessions` | PC | 匿名 + `qr_ctx` | 建票，响应 `Set-Cookie: qr_ctx`（`Path=/api/qr`） |
| `GET /api/qr/sessions/{ticket}` | PC | qr_ctx | 轮询，**只读无副作用** |
| `POST …/claim` | PC | qr_ctx | **唯一**下发 `idp_session` 的端点 |
| `POST …/cancel` | PC | qr_ctx | 作废换码 |
| `GET …/preview` | 手机 | 身份 | 取"要被登录那台机器"的画像 |
| `POST …/scan` | 手机 | 身份 | 标记已扫码 |
| `POST …/confirm` | 手机 | 身份 | **唯一的授权动作**，无请求体 |
| `POST …/refuse` | 手机 | 身份 | 「不是我操作」 |

手机侧身份在 `controller/qr` 的 `resolveIdentity` 里合并两条路：**Bearer access_token**
（原生 App）与 **`idp_session` Cookie**（H5 兜底页）。

> **轮询与领取为什么是两个端点**：手机也要查状态。若查询自带"命中 confirmed 就发 Cookie"
> 的副作用，手机打开确认页的那一次查询就会把会话建立到手机上（`Set-Cookie` 落在手机），
> PC 永远领不到。读写分离后只有 PC 会调 claim。

## 安全支点：`qr_ctx` 把票据绑回创建它的浏览器

建票时给 PC 下一个 HttpOnly Cookie，**库里只存它的 SHA-256**；领取时必须匹配。

没有它，二维码就是"谁扫都能用"的凭据：攻击者把 PC 上的码截图发给任一已登录的受害者，
受害者一扫，攻击者的浏览器就拿到受害者会话。**票据 256 bit 熵在这个场景毫无用处，
因为扫描者是自愿扫的。** 有了它，领取必须由当初那张码所在的浏览器发起。

同理 **`return_to` / `client_id` 不入表、也不下发给手机**：票据只代表"某台 PC 想登录"，
不代表登录完要授权哪个应用。一旦把授权请求绑进 ticket，攻击者就能构造一张
"`/oauth2/auth?client_id=攻击者应用` 的二维码"让受害者替他完成授权 ——
那时扫码就从"登录方式"退化成"授权代理"。

### bad_eg：只检查"带了 qr_ctx"

```go
// ❌ 攻击者创建过自己的票据，因此手里有一枚合法 qr_ctx，拿去领别人的
if ctxPresent { allow() }
```

```go
// ✅ 必须是"这张票当初那一个"
q = q.Where(cols.CtxHash, sha256(callerCtx))
```

**这条必须单独测**：`forward_attack`（无 ctx）通过不代表 `ctx_not_interchangeable`
（用自己的 ctx 领别人的票）也通过。两项合起来才等于"绑定"。

## 状态机：迁移一律条件 UPDATE

`pending → scanned → confirmed → consumed`，另有 `cancelled` / `expired` 终态。

每一步都是 `UPDATE … WHERE <前置状态> AND expires_at > now()`，看 `RowsAffected()` 定胜负。
**绝不允许**先 SELECT 判断再无条件 UPDATE —— 那样两个并发请求会双双通过判断。

```sql
-- claim：三个条件写在同一条 UPDATE 里
UPDATE qr_login_sessions SET status='consumed', consumed_at=$now
 WHERE ticket=$1 AND status='confirmed' AND ctx_hash=$2 AND expires_at > $now;
```

> 现有 `ConsumeAuthorizationCode`（`logic/oidc`）正是读后写的形状。它在授权码上问题不大
> （还有 PKCE 兜底），但 claim 直接决定谁拿到登录态，**不能照抄**。

**顺序**：先抢态成功、再建会话。反过来会留下多条只有第一条被记录的僵尸会话，
而每一条都带真实账号的权限。

### 过期不靠定时任务写库

`EffectiveStatus()` 在**读取侧**把"`expires_at` 已过"折叠成 `expired`。库里不存这个值。
若只靠定时改写，服务重启期间没人跑批，会出现"早过期了但状态还是 pending"的行 ——
症状是前端一直转圈，而排查的人以为是轮询坏了。

## 防探测的遮蔽边界（这条曾经划错）

无 `qr_ctx` 的调用方轮询时，**只遮蔽 `status`（一律回 pending），不遮蔽 `expires_in`**。

```go
// ❌ 曾经这样：连 expires_in 一起留零值
return &View{Status: QRStatusPending}, nil
```

前端每次轮询都用 `expires_in` 覆盖倒计时，于是只要有一次请求没带上 Cookie，
屏幕立刻显示"0s 后失效"，而票据其实还活着 —— **不报错、不拒绝，只是把用户挡在门外**，
最难归因。而且剩余寿命本来就不是秘密：建票响应里已公开给任何拿到这张码的人。

> 一句话：**要遮的是"进展到哪一步"，不是"这张码还剩多久"。**

## 限流（`internal/limiter`，进程内令牌桶）

| 端点 | 键 | 速率 | 依据 |
|---|---|---|---|
| 建票 | 来源 IP | 10/分钟，突发 20 | 一张票活 120s，一分钟建到第 11 张意味着前 10 张一张没被扫 |
| 批准 | 批准者账号 | 30/分钟，突发 60 | 一次批准 = 给别人一台机器发该账号的会话 |

两处刻意不做：

- **不给轮询设 IP 限**：轮询正常频率就是每 1.5 秒一次（约 40 次/分钟），
  一个公司出口 NAT 后十个人同时登录就能把共享 IP 打到 429 —— 那是把防护做成自我拒绝服务。
- **不加全进程总量桶**：听起来防分布式灌表，实际是把资源问题换成可用性问题，
  一个攻击者就能让所有人登录不了。

定位：**把滥用从免费变成有成本**，不是抗 DDoS。把它当后者会得出"上了限流就安全了"
的错误结论。

限流判定放在控制器逐端点做，没走分组中间件 —— 八条端点合理频率差着量级，
同一个桶要么放过刷票要么打断轮询。代价是"新增端点忘了设限流"没有兜底。

## 移动端 App 的"两份凭据"形态

App 同时持有、各管一件事：

| 凭据 | 用途 | 有效期 |
|---|---|---|
| 统一登录平台登录态 `idp_session` | 批准扫码；静默换业务 token | 8h（可配） |
| 业务后端 JWT | 所有业务接口 | 后端自己的策略（30 天） |

换业务 token 全程无需用户参与：拿登录态静默走 `authorize + consent` 得到 code，
把 `code + code_verifier` 交给业务后端已有的 `/user/oidc/callback`。
后端用它自己的 client 身份去认证中心换 token，**那批 token 留在后端、不下发给 App**。

> **为什么登录态是会话而不是 access_token**：会话在服务端是 `user_sessions` 一行，
> **可被立刻吊销**（RP 发起登出、管理员处置被盗账号都会删它）。而 App 不是任何人的
> 依赖方，它只是想要一个登录态 —— 为它维持一条 token 生命周期毫无必要。

### 一个凭据只服务一个用途

这条是踩出来的，不是审美：把"业务会话"和"一次性动作身份"压在同一枚 access_token 上，
它的 10 分钟有效期同时满足不了两边，接着就衍生出「要不要存 refresh_token」
「失效太快要不要调 TTL」两层伪问题 —— **那都不是需求，是第一个错误的派生物。**

### bad_eg：用调平台级安全参数去修客户端体验问题

```
症状：App 十几分钟就要重新登录
❌ 反应：把 auth-hub 的 AccessTokenTTL 从 10 分钟调到 8 小时
   → 影响全部 5 个客户端的安全参数，而问题只出在一个客户端的架构上
✅ 反应：摆正凭据分工（登录态 vs 业务 token），TTL 不动
```

顺序永远是**先摆正架构，再考虑调参数**。用户会直接指出"你有点奇怪"。

## 静默同意：第一方域的正当豁免

认证中心的 consent **没有任何"已授权过就跳过"机制** —— 每次 authorize 都要求显式决定。
App 侧自动提交 `decision: allow` 意味着用户从没见过授权页。

这是**被规范承认的情形**：RFC 9700 反对的是公开客户端上的静默同意；同一管理域内的
第一方客户端跳过同意是标准做法。收益也真实 —— 新增一个后端只要"注册 client +
暴露 `/user/oidc/config`"，App 侧一行不改，适合横向扩。

**随之而来的变化必须记住**：同意不再由人把关之后，**信任锚点从"用户点同意"移到了
"谁能注册成 client"**。以后真正要守的门是认证中心的管理端注册接口。

若哪天要收紧，优先级排序也在这里：同一个 http 通道上 APK 分发也是明文且客户端无哈希固定，
能改写 `/user/oidc/config` 的位置同样能换掉更新包 —— 真要投入，HTTPS 或制品签名
比给同意加弹窗划算得多。

## 操作记录

### 2026-10-11 由一次真实实现沉淀

| 错误操作 | 实际后果 | 正确做法 |
|---|---|---|
| 把防探测理解成"无凭据者什么都不该看到"，连 `expires_in` 一起遮蔽 | 前端倒计时塌成"0s 后失效"，用户以为二维码坏了；不报错、不拒绝，最难归因 | 遮蔽范围精确到"进度"；剩余寿命不是秘密，照实返回。补断言：无 ctx 时 `expires_in` 必须是真实值 |
| 给"设备画像全空"写测试时只测解析层（喂理想 payload） | `preview()` 少写 `/preview` 后缀、打到 PC 侧轮询端点这件事完全没被发现；那个端点 200、`code=0`、只是没有 `pc` 字段 → 确认按钮被自己的安全规则禁掉 → 功能整体不可用且无任何报错 | 测**请求 path**（MockClient 记录 URL 逐端断言），而不是测响应解析。测错层位的测试等于没测 |
| 手机侧端点签名保留 `String accessToken` 形参，只是改语义去收登录态 | 调用方继续传业务 token **仍通过类型检查**（都是 String），要等运行时 401 才发现 | 把凭据从签名里彻底拿掉，端点自己从注入的存储取。传错就编译失败 —— 编译器比约定可靠 |
| 新加的安全断言直接宣称"已验证" | 其中一条测试在服务不可达时是 `return` 跳过，本地服务停掉后那次"All tests passed"什么都没验证 | 安全断言必须做**负向对照**：临时移除被守卫的实现，确认真会变红，再恢复复验 |
